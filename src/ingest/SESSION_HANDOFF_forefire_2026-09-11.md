## 1. Commit `f596b33` — stale netcdf symlinks in sweeps

Carried over from the previous session, committed today.

`sweep_ff_params` linked staged netcdfs with `if not os.path.exists(link)`.
Wind-scaled files live in `nc_<grid_code>_w<scale>/` but keep **identical
filenames**, so a symlink left by an earlier scale survived into the next
parameter set and silently served the wrong winds. The failure mode is the
dangerous kind: every run looks plausible and every run is wrong.

It now compares the link target and replaces on mismatch. Only symlinks are ever
unlinked — a real file at that path is left alone, because the unscaled path
copies the workspace netcdf in directly.

Regression harness over both orderings: staging `w1` then `w4` into one run
directory served `UNSCALED` then `UNSCALED` before, `UNSCALED` then `SCALED4`
after.

## 2. The definitive fuel table

`/home/jhaley/forefire/tests/ff_fuels_behave13.csv`, 1,903 bytes, 14 rows, ASCII,
no CR bytes. Generated by `fuel_table_from_namelist` (§23 of 09-10) from
`etc/nlists/default.fire_behave_13`. Regenerating gives md5 `9a9221fd4ac6…`
both times, so it is reproducible from the namelist rather than hand-edited.

`etc/forefire.json` line 19 now points at it. `fuelstrans.csv` is untouched on
disk, so reverting is a one-line change.

### Why this was worth doing at all

`fuelstrans.csv` was never a calibrated artifact. It is a mapping of the
40-category Scott & Burgan models onto the nearest of the 13 Anderson categories
(09-10 §22), binned to six SAV levels, with category 2's load inconsistent with
its own neighbours. It existed to make ForeFire run. Every WRF-SFIRE forecast,
meanwhile, ships a `namelist.fire` stating the fuel properties it actually used.

The aim is **not** to make ForeFire reproduce WRF-SFIRE — different spread
formulations, it never will — only to stop the two disagreeing about the fuel
they were both handed.

### What ForeFire's Rothermel actually reads

Verified against the container source this session, `src/propagation/Rothermel.cpp:150-231`.
The model registers 24 fuel properties and **uses seven**:

| used | ignored (registered, never read in `getSpeed`) |
|---|---|
| `Rhod`, `Md`, `sd`, `e`, `Sigmad`, `DeltaH`, `me` | `Rhol`, `Ml`, `sl`, `Sigmal`, `Blai`, `stoch`, `RhoA`, `Ta`, `Tau0`, `Cp`, `Cpa`, `Ti`, `X0`, `r00`, `Deltah` |

This settles a worry about the mapping. `default.fire_behave_13` has no
`fmc_gw05`, so the generator puts all of `fgi` in the dead pool and zeroes
`Sigmal`. **That is inert** — `Sigmal` is never read. It also means the
live/dead split is not a lever in this model at all, and the CAWFE variant's
`fmc_gw05` buys nothing for ForeFire.

It also confirms the unit chain: `lsd = valueOf[sd] / 3.2808399` proves `sd` is
in 1/m, so `savr` (1/ft) × 3.28084 is the right direction.

### The mapping, and what moved

## 3. Re-baseline sweep on SINLAHEKIN

Everything before this ran on `fuelstrans.csv`. This re-derives the `pSAF` × `Md`
ridge on the new table so later work has a starting point with no tuned quantity
in it.

Setup: corrected ignition `48.70375, -119.70506` (09-10 §5), overridden in memory

skipped because it equals `me` for categories 2 and 11 in the derived table just
as it did in the base one, making `Etam` identically zero; 0.14 is used instead.

### The slice had to be re-derived, and this is a trap

`d6b03a8` moved `make_timing_table`'s reference from the first wrfout to the step
bracketing ignition. Confirmed live this session: row 6 (21:00Z) gets
`ign_seconds` 679 = exactly 21:11:19 − 21:00:00.

**Consequence: `ign_seconds` is now seconds from the 21:00Z wrfout, not from
ignition.** The 05:50Z observation is therefore at **31,800 s (+8.83 h)** in the
run reference, not the 31,104 s (+8.64 h) used before.

The old script's `SLICE_ROWS = 22` meant a 10.5 h horizon before the fix and
means **7.5 h** after it. Carried over unchanged it would have stopped 1.3 h
short of the observation and reported every cell as "not reached" — a silent,
plausible-looking wrong answer. 26 rows was derived from the table instead
(row 25 = 06:00Z, one step past the observation).

**Any script written before `d6b03a8` that hardcodes a row count or an
observation time in seconds is wrong until re-derived.**

### The ridge, as predicted

Four of 25 land within ±25%, and they lie on a clean diagonal:

| pSAF | Md | area | ratio | IoU |
|---|---|---|---|---|
| 0.3 | 0.10 | 179 ha | 0.98× | 0.62 |
| 0.4 | 0.12 | 212 ha | 1.16× | 0.67 |
| 0.5 | 0.14 | 187 ha | 1.02× | 0.62 |
| 0.3 | 0.08 | 209 ha | 1.14× | 0.66 |

**ΔMd ≈ +0.02 buys ΔpSAF ≈ +0.1.** This is the degeneracy 09-09 §5 predicted from
the code and it survives the fuel-table change: `pSAF` multiplies node speed and
`Md` acts on `R0`, which multiplies the same bracket, so one area at one time
cannot separate them. **A single best fit here would be false precision — the
ridge is the deliverable.**

`Md` 0.18 collapses every row to 0.11–0.34×, consistent with the 09-09 finding
that this fire barely moves above `Md` ≈ 0.15.

At the template defaults (`pSAF` 0.6, `Md` 0.10) the model gives **602 ha,
3.28× the observation**. That is a statement about the parameters, not the table.

### Shape is unchanged, which is the expected result

|  | mean IoU | best IoU |
|---|---|---|
| `fuelstrans.csv` | 0.680 | 0.699 |
| namelist-derived | 0.670 | 0.713 |

Per-cell deltas run −0.07 to +0.04 with no pattern — negative at low `pSAF`,
positive at high. **This is noise, not a signal**, and it is what should be
expected: the table changes how much fuel and how fine it is, which moves *when*
the fire reaches a given size, while IoU is scored at matched area and so divides
that out.

The structural shape gap is untouched: modelled elongation **1.38–1.57** against
the observed **2.54**, essentially the 1.42–1.80 of 09-10 §6. The fuel table was
never going to fix that (09-10 §26 items 2 and 3 — spotting, which ForeFire
cannot produce standalone).

### What this does and does not establish

It **does** establish where the ridge sits on a defensible fuel basis and on a
corrected clock, which is the starting point later tuning needs.

It does **not** establish that the derived table is better. One fire cannot do
that, the fuel-mix argument in §2 says why, and the table's justification is its
provenance in the first place. SINLAHEKIN is ~17% timber-grass, 33% brush, 35%
litter, 15% closed timber — a mix where the table's changes partly cancel. A
grass-dominated fire would move much more; Smokehouse measured 1.29× in area at
fixed parameters (09-10 §23), and that fire is now parked as an outlier.
