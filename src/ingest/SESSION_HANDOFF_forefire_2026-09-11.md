## 1. Commit `f596b33` — stale netcdf symlinks in sweeps

Carried over from the previous session, committed today.

`sweep_ff_params` linked staged netcdfs with `if not os.path.exists(link)`.
Wind-scaled files live in `nc_<grid_code>_w<scale>/` but keep **identical
filenames**, so a symlink left by an earlier scale survived into the next
parameter set and silently served the wrong winds. The failure mode is the
dangerous kind: every run looks plausible and every run is wrong.

It now compares the link target and replaces on mismatch. Only symlinks are ever
unlinked — a real file at that path is left alone, because the unscaled path
copies the workspace netcdf in directly.

Regression harness over both orderings: staging `w1` then `w4` into one run
directory served `UNSCALED` then `UNSCALED` before, `UNSCALED` then `SCALED4`
after.

## 2. The definitive fuel table

`etc/ff_fuels_behave13.csv`, 1,903 bytes, 14 rows, ASCII,
no CR bytes. Generated by `fuel_table_from_namelist` (§23 of 09-10) from
`etc/nlists/default.fire_behave_13`. Regenerating gives md5 `9a9221fd4ac6…`
both times, so it is reproducible from the namelist rather than hand-edited.

Both `etc/forefire.json` and the tracked `.initial` point at it; a copy also sits
under `bind_host` at `/home/jhaley/forefire/tests/`. `fuelstrans.csv` is untouched on
disk, so reverting is a one-line change.

### Why this was worth doing at all

`fuelstrans.csv` was never a calibrated artifact. It is a mapping of the
40-category Scott & Burgan models onto the nearest of the 13 Anderson categories
(09-10 §22), binned to six SAV levels, with category 2's load inconsistent with
its own neighbours. It existed to make ForeFire run. Every WRF-SFIRE forecast,
meanwhile, ships a `namelist.fire` stating the fuel properties it actually used.

The aim is **not** to make ForeFire reproduce WRF-SFIRE — different spread
formulations, it never will — only to stop the two disagreeing about the fuel
they were both handed.

### What ForeFire's Rothermel actually reads

Verified against the container source this session, `src/propagation/Rothermel.cpp:150-231`.
The model registers 24 fuel properties and **uses seven**:

| used | ignored (registered, never read in `getSpeed`) |
|---|---|
| `Rhod`, `Md`, `sd`, `e`, `Sigmad`, `DeltaH`, `me` | `Rhol`, `Ml`, `sl`, `Sigmal`, `Blai`, `stoch`, `RhoA`, `Ta`, `Tau0`, `Cp`, `Cpa`, `Ti`, `X0`, `r00`, `Deltah` |

This settles a worry about the mapping. `default.fire_behave_13` has no
`fmc_gw05`, so the generator puts all of `fgi` in the dead pool and zeroes
`Sigmal`. **That is inert** — `Sigmal` is never read. It also means the
live/dead split is not a lever in this model at all, and the CAWFE variant's
`fmc_gw05` buys nothing for ForeFire.

It also confirms the unit chain: `lsd = valueOf[sd] / 3.2808399` proves `sd` is
in 1/m, so `savr` (1/ft) × 3.28084 is the right direction.

Note the changes are **not one-directional**. Grass and timber-grass get more
load and finer fuel; tall grass (3) and chaparral (4) lose SAV and load
respectively. A fire's response therefore depends on its fuel mix, which is why
one fire cannot adjudicate the table.

### Verified through the live path

`load_ff_cfg` resolves it; `write_fuel_table(0.06, cfg)` produces a table
differing from the base in the `Md` column alone, LF endings throughout, 0 CR
bytes; `container_path` maps it inside the apptainer bind. The CRLF trap from
09-08 does not recur.

### Where it takes effect — and where it does NOT

The table is checked in at **`etc/ff_fuels_behave13.csv`**, and both
`etc/forefire.json` and the tracked `.initial` point at it.

**`cfg['fuels_table']` is read by Python only.** `write_fuel_table` and
`fuel_table_from_namelist` `open()` it; it is never passed through
`container_path`, so it does not have to sit under `bind_host`. That is why a
repo path works.

**But the `.ff` templates hardcode their own:**

```
/home/jhaley/forefire/tests/ignition_template.ff:6:setParameter[fuelsTableFile=/forefire/tests/fuelstrans.csv]
/home/jhaley/forefire/tests/restart_template.ff:6:setParameter[fuelsTableFile=/forefire/tests/fuelstrans.csv]
```

`apply_ff_params` overrides that line when a `fuelsTableFile` parameter is
passed — which `moisture_params` does, and which every sweep does. With moisture
disabled and no params, **nothing overrides it and ForeFire reads
`fuelstrans.csv` from inside the container.**

So as of this commit the derived table governs the sweeps and the moisture path,
and **not a default `run_forecasts` run**. Closing that needs one of:

- point the templates at `/forefire/tests/ff_fuels_behave13.csv` and keep a copy
  under `bind_host` (the file is already there, same md5), or
- have `make_script_set` always emit `fuelsTableFile`, which means the base table
  must be bind-visible and the repo copy becomes the master to copy from.

The templates are untracked and live outside the repo, so this was not decided
here. **Until it is, do not assume an operational forecast used the derived
table.**

The live config also has no `wind_scale` key; `float(cfg.get('wind_scale',1.0) or 1.0)`
reads the absence as 1.0, so behaviour is right, but the key must be added by
hand before winds can be scaled.

## 4. Spread-rate targets: what a defensible one requires

This is the note James asked for. **Every observed-spread target in the 09-10
handoff should be treated as unsupported until re-derived**, and the method below
is what a replacement has to satisfy.

### Why the existing ones fail

| source | claim | why it fails |
|---|---|---|
| 09-10 §15 | 0.5–0.83 m/s "defensible observed target" | assumes 3.3 h / 8.3 h windows and "64.8 km in 16.5 h"; the incident-filtered GOES rows span **3.25 h** (20:41Z–23:56Z) on both `acq_date_time` and `pixel_date_time`. Contradicts §10, which has the span right. A reconstruction on the real span gives connectivity 1.00 everywhere and 1.1–8.5 m/s. |
| `perim1.pkl` / `perim2.pkl` | 3.4–4.4 m/s | polygons drawn around detections, not IR perimeters. 246,203 ha over a 130 km cloud is a hull, mostly unburned. **Withdrawn.** |
| scan-to-scan differencing | 23–55 m/s | association noise; a 2.7 km pixel locates a front to half a pixel and fire burns between scans without lighting a new one. |

**09-10 §26 item 12 — "the formulation needs 4.3×" — inherits §15's target and
falls with it.** Do not quote the 4.3× multiplier.

### What a target needs

1. **A single-origin fire.** Smokehouse is a 246,000 ha complex already mature at
   the first scan; the nearest-origin assignment then measures cluster
   separation, not spread. Park it (James: *"In many ways this is an outlier
   event"*).
2. **Both guards from `ros_estimate2.py`.** Cluster the first scan, then require
   connectivity — the fraction of a cluster's detections reachable from its
   origin through ≤ 4 km hops. Below ~0.5 the number is the diameter of the
   complex over elapsed time and must be rejected, not reported.
3. **A stated sensor.** VIIRS at 375 m locates a front ~7× better than ABI at
   2.7 km. A target from VIIRS and a target from GOES are not the same
   measurement and should not be pooled.
4. **A stated window.** Rates fall as the window lengthens — the head outruns the
   mean. Quote the window with the number, always.
5. **A direction.** The rate is an average along the fastest axis and so is a
   **lower bound** on the instantaneous peak. Say so.

### Then, and only then

Compare against ForeFire's ceiling in the relevant fuel (2.66 m/s in fuel 2 at
the winds measured, 09-09 §5b) to decide whether the gap is reachable by wind at
all, or whether it is a formulation limit. That decision was made once on §15's
numbers and has to be made again.

**TELEPHONE (active, VIIRS available) is the natural first case** — single
origin, 375 m detections, and a live forecast to compare against. Done: §5.

### A trap in `write_fuel_table`, found the hard way

The first attempt returned **byte-identical results for two arms that differed
only in base table**. `write_fuel_table` names its output by `Md` alone —
`run_dir/fueltables/fuels_Md_<md>.csv` — so two arms at the same `Md` from
different base tables write the same path and the second silently wins. Both
moisture arms had run the derived table; the `fuelstrans`/0.0226 cell never ran.

Re-run with a per-arm `run_dir`, and asserted on `sd` before spending the runs.
**Any sweep varying the base table must give each arm its own `run_dir`**, or
`write_fuel_table` needs the base in its filename.

`…-30/forefire/grid_nml.csv`, `nml_rebaseline.py`.

## 6. The FMDA moisture chain, and the geogrid conversion

Chasing why moisture made TELEPHONE worse led into the FMDA path. Three findings,
two commits.

### The negatives are upstream, not from the conversion

`resolve_md` returned a **negative** SAV-weighted moisture and its fail-closed
gate correctly rejected it. Reading the source netcdf
`/data/WRFXPY/wksp_fmda/CONUS/202609/fmda-CONUS-20260910-19.nc`, `FMC_GC` is
(1258, 2145, **5**) = `[m1, m10, m100, dEd, dEw]`:

| layer | min | max | mean | % < 0 | |
|---|---|---|---|---|---|
| 0 | −0.0912 | 0.7876 | 0.0839 | **3.48** | 1h |
| 1 | −0.0382 | 0.6645 | 0.1197 | 0.24 | 10h |
| 2 | 0.0189 | 1.2054 | 0.2217 | 0.00 | 100h |
| 3 | −0.2573 | 0.1099 | −0.0647 | 93.68 | `dEd` |
| 4 | −2.4603 | 0.1283 | −0.1763 | 78.63 | `dEw` |

The same **3.48%** appears in the written tile, so the conversion copies them
through faithfully. **The assimilation itself drives 1h below zero** in the driest
cells; layers 3–4 are signed equilibrium adjustments and are fine. The ordering
1h < 10h < 100h is correct for drying, and 96.5% of the field is physical.

At TELEPHONE: 1h −0.0135, 10h 0.0226, 100h 0.1128. **FMDA says this site is
drier than the fuel table's `Md` = 0.10**, which is why §5's moisture arms
overshoot. The 10h value was used as the driest physically valid reading.

James's plan is a fresh pull of the latest wrfxpy and a new assimilation; the
below is the interim.

### `make_geo_folder` put a non-moisture into a moisture slot

`from_netcdf` builds `m_ext = [m1, m10, m100, dEd, dEw]` (width 5). The old
`make_geo_folder` widened to 6 leaving `[…, dEd, dEw, 0]`, and `to_geogrid`
writes `FMC_GC[:,:,:-2]` — four slices at n=6 — so **`dEd` landed where geogrid
reads a moisture class.** Both shapes exist on disk:

```
fmda-CONUS-20260910-20.geo   FMC_GC z=6, FMEP z=2   <- make_geo_folder's output
everything else sampled      FMC_GC z=5, FMEP z=3   <- another producer
```

Measured on the z=6 tile: layer 3 mean **−0.0653, negative over 93.8%**, against
0.0000 on the z=5 tiles. TELEPHONE's tile (`-19`) is a z=5 one, so it never went
through the conversion. What writes the z=5/z=3 folders is **not established** —
FMEP z=3 matches no branch of the current `to_geogrid`.

### The fix (`1bbe877`, `0389e28`)

`namelist.fire` declares `moisture_classes = 6`, so three classes must be added,
**after `m100` and before the parameters**. `to_geogrid` keeps the last two
slices for its lon/lat test, so six filled classes need `m_ext` **eight** wide:

```
m_ext = [m1, m10, m100, 0.1, 0.3, 0.3, dEd, dEw]
FMC_GC -> 8 layers, first six the classes, last two zero
FMEP   -> [dEd, dEw], matching source exactly
```

`0.1, 0.3, 0.3` (1000h, live herbaceous, live woody) are **standing values, not
analysis**, commented as such: zero is not a neutral default for fuel moisture,
it is the most flammable one. Negative moisture is clamped to zero with a printed
count — 100,416 values, 1.24% of the dead classes on the 19Z tile. Per James,
**one negative makes wrfxpy discard the whole array and use zeros**, so the clamp
protects the other 98.8% rather than repairing anything.
